# Sell the feature key, not dashboards

**Do not build the full design-to-monitoring platform as a SaaS now. Build something narrower, and only after the free CLI shows real pull.** Six research tracks covering about 50 products found no platform that organizes the SDLC by feature, meaning one durable feature record that holds design, spec, tasks, code, tests, release and monitoring. None of them shows one feature end to end in a single view either. The closest attempts each cover about half the lifecycle: Atono, Azure DevOps's "Feature" work item, Reflag (formerly Bucket) and Linear. The gap is real. But every stage of that chain already belongs to a well-funded incumbent, and those incumbents are expanding into the stages next to them. Linear now tracks issue → PR review → deploy. LaunchDarkly, PostHog, Datadog and Sentry are moving from production back into PRs. Figma is syncing the canvas with repositories. Atlassian has opened a cross-tool graph to outside agents. Three other facts argue against the full vision. The money in this space goes to whoever owns the system of record (Atlassian paid about $1B for DX), while visualization-only tools like CodeSee were absorbed. "Single pane of glass" products tend to fail because nobody uses them every day. And features-cli has almost no public adoption yet: **11 GitHub stars, 0 forks and 140 crates.io downloads in 90 days**. Nobody has unified the lifecycle partly because "feature" means something different in each camp: a planning container, a flag, a UI click target, a spec folder, or a cluster of files. What features-cli has that nobody else has is a *feature key* derived automatically from folder structure and kept in the repository. That key exists as soon as the code does and outlasts the story, the flag and the project, so it can join specs, owners, coverage, flags, errors and usage. The SDLC-by-feature framing therefore keeps the verdict but changes the positioning. The product should be a **feature system of record built around a shared feature ID**, with features-cli's key proposed as the open standard, not a dashboard. Its first paid product should be **health checks for AI-heavy monorepos**: trends over time, cross-repo rollups, PR gates, and spec-drift and flag-hygiene signals, delivered mainly into pull requests and agent context rather than a dashboard people have to visit. A wave of tiny open-source projects that declare features in YAML files inside the repo, for AI agents, supports the in-repo approach. They also have almost no stars. Price the hosted tier at roughly **$15–25 per active contributor per month**, and gate it on a 90-day CLI launch and design-partner test with explicit kill criteria.

A note on evidence quality before the analysis. Every research track was blocked from fetching key vendor sites (linear.app, posthog.com, launchdarkly.com, swarmia.com, linearb.io, port.io, atono.io, tggl.io, npmjs.com, hn.algolia.com, the YC directory, and the GitHub API for unattached repositories). Facts about Atono and the small open-source repositories therefore come from search snippets, documentation pages and directory listings. Most prices come from aggregators that often disagree with each other. Funding totals conflict across PitchBook, Tracxn and CB Insights. Much of the criticism of SEI tools and portals is written by competitors. Statements like "no vendor does X" mean no evidence turned up in a limited search, not proof that the capability is absent. No customer interviews were run. The recommendation below accounts for these limits.

## Does an SDLC-by-feature platform exist? Not yet

**No.** A dedicated research pass tried to disprove the earlier finding and failed. It looked for any commercial or open-source product, active as of November 2026, that makes a code-level feature its primary entity and attaches design, spec, tasks, PRs, tests, release and flags, and production usage and errors to that one record. It found none. What does exist is a set of products that use "feature" as their main noun for one segment of the lifecycle. Ranked from most to least lifecycle coverage:

| # | Product | What "feature" means there | Stages covered | Missing |
|---|---|---|---|---|
| 1 | **Atono** (private startup, Toronto) | A story with feature flags attached | Plan → build → flag rollout (OpenFeature-based) → claimed "measure"; GitHub PR linking (low-confidence listing); MCP server | The story closes when the work is done, so no durable feature remains. No error or production telemetry found. No spec or design artifact |
| 2 | **Azure DevOps Boards "Feature"** (Microsoft) | Planning tier: Epic > Feature > Story | Branches, commits, PRs and builds (Development control) → release stages (Deployment control) → test plans | Code links sit on child items. The Feature has no module or path identity, no usage or error data, and no living spec |
| 3 | **Reflag** (formerly Bucket.co) | A feature key in code | Release stages (In development → Internal → Beta → GA) → targeting → adoption → feedback; MCP | No spec, design, tasks or PRs. No error tracking. The lifecycle starts when the flag is created, not at the idea |
| 4 | **Linear** (2026: Diffs + Releases) | Issue / project | Plan → in-app code review → release pipelines and notes | No flags, usage or errors. Projects end at ship, so no living feature record remains |
| 5 | **Planview Viz** (Flow Framework) | A flow-item type ("Feature", alongside Defect, Risk, Debt) | Flow metrics from "concept to cash" across connected tools | Analytics overlay only. Holds no artifacts and has no code identity |
| 6 | **Kiro / OpenSpec / dspec** | A spec folder (`requirements.md`, `design.md`, `tasks.md`) or a change folder | Spec → design → tasks → code. dspec fingerprints the code symbols a spec references | No release, flag, usage or error stages. No team UI |
| 7 | **ProductMap AI** | A feature tree inferred from code | Code understanding only | No planning, release or production stages. Traction unclear since launch |
| 8 | **Serenity BDD** (open source) | Capability > Feature > Story test folders | Gherkin specs ↔ test results | No PRs, releases, flags or usage |
| 9 | **Kosli** | A flow or trail keyed by commit, PR or ticket | Commit → build → attestations → what runs in production | Organized around changes and compliance, not features |

No funding or traction data was found for it. Microsoft says linking work items to builds and releases provides "an audit trail of the feature development and deployment" ([MS Learn](https://learn.microsoft.com/en-in/azure/devops/cross-service/end-to-end-traceability?view=azure-devops)). Reflag's default release stages and adoption tracking hang off one feature key ([Reflag docs](https://docs.reflag.com/product-handbook/feature-rollouts)), and it has raised about $5.7M ([Reflag](https://reflag.com/blog/bucket-reflag)). Linear's Diffs changelog promises to "ship code from Linear" ([Linear changelog](https://linear.app/changelog/2026-05-27-linear-diffs)). Planview's Flow Framework defines Features as one of four flow-item types ([Planview](https://www.planview.com/products-solutions/products/viz/)). dspec measures drift through `codeRef` symbol fingerprints "so drift is measured rather than remembered" ([GitHub](https://github.com/tuna781/dspec)), and OpenSpec gives each change its own folder ([GitHub](https://github.com/Fission-AI/OpenSpec)). ProductMap AI launched on Product Hunt in May 2025 with 175 upvotes ([Product Hunt](https://www.producthunt.com/products/productmap-2)). Serenity renders requirements as capabilities, features and stories ([Serenity docs](https://serenity-bdd.github.io/docs/reporting/living_documentation)). Kosli matches artifact fingerprints to environments ([Kosli docs](https://docs.kosli.com/understand_kosli/how_kosli_works)).

Azure DevOps sitting at number two shows that **the concept is old**. Agile and SAFe hierarchies have had a "Feature" tier for years. What was never built is a version of that feature that starts from the code and carries telemetry. No company in the 2025 YC batch round-ups works on feature lifecycle or spec-to-production tracking ([CB Insights](https://www.cbinsights.com/research/y-combinator-summer2025/)). 2026 developer-tool funding has gone to verification, agent governance and coding agents instead ([Unite.AI](https://www.unite.ai/and-truth-raises-70m-seed-to-build-universal-verification-machine-for-code/); [TechCrunch](https://techcrunch.com/2026/09/01/air-raises-50m-to-help-companies-vet-the-skills-and-add-ons-ai-agents-use/)). Searches for "feature inventory" software returned only tools that inventory the SaaS apps a company buys, not the features it builds ([Bruin](https://getbruin.com/use-cases/saas/feature-deprecation-impact/)).

### Five camps use the word "feature" for five different things

The main reason nobody has unified the lifecycle is that **each camp means something different by "feature"**, and each meaning lasts a different length of time. In planning tools a feature is a work-item container: the Azure DevOps or SAFe Feature, or a Linear project. It closes when the work ships. In flag tools a feature is a runtime switch. Unleash and Tggl market "feature lifecycle management", and by that they mean the life of a flag, which ends at flag cleanup ([Unleash](https://www.getunleash.io/blog/feature-lifecycle-management); [Tggl](https://tggl.io/feature-lifecycle-management)). In analytics a feature is a UI click target. Pendo lets teams "tag a page or feature anytime" after the fact ([Pendo](https://www.pendo.io/pendo-vs-amplitude/)), while in Amplitude and Mixpanel a feature is an analysis over named events with no feature object behind it ([Userpilot](https://userpilot.com/blog/pendo-vs-amplitude/)). In spec tools a feature is a folder of Markdown that gets archived. In code mappers it is an inferred cluster of files. Every camp claims its own unit is the real feature. LaunchDarkly, for instance, argues that monitoring tools track application health "but not feature behavior" and that flags should fill that gap ([LaunchDarkly](https://launchdarkly.com/blog/core-capabilities-enterprise-feature-management-platform/)).

The traceability problem shows up in research as well as in tooling. An arXiv study of open-source GitHub projects found that "a large portion of documented features did not offer linked implementation" ([arXiv](https://arxiv.org/pdf/2208.01317)). **The missing primitive is a durable feature ID that all five camps can reference** and that outlives any one story, flag or spec. A code-derived key is the only one of these units that exists as long as the code does.

### Developers are hand-building feature registries in YAML

The newest signal comes from developers themselves. Across 2025 and 2026, a scattering of tiny open-source projects started declaring features in files inside the repository, mostly framed as context or memory for AI coding agents. Amvelt TRACE maps a repo "by features, capabilities, and system boundaries". It infers features from routes, directories and the syntax tree, or reads `.codebase/features/*.yaml`, and gives agents context slices and CI rule checks. It has **0 stars and 13 commits** ([GitHub](https://github.com/anubhav-n-mishra/ABS-Trace)). One feature-map project keeps a `FEATURE-MAP.yaml` of business flows and audits drift as GAP, DRIFT, IMPACT or OK, packaged as a Claude Code plugin and Codex skill ([GitHub](https://github.com/ade-syofyan/feature-map)). Another, also called feature-map, keeps `.features/*.yaml` with a CLI that validates that the referenced paths exist ([GitHub](https://github.com/markschellhas/feature-map)). feature-registry catalogs features, flags with sunset reminders, and Jira and Confluence links, but does not link to the code repository. It also has **0 stars** ([GitHub](https://github.com/dzanfardino/feature-registry)). Issue threads in other projects propose the same pattern, such as a `.g8s/feature-map.yml` linking user stories, code paths and tests, checked in CI ([g8s #649](https://github.com/tamld/g8s/issues/649)).

These projects matter in three ways. First, they are a **demand signal**: developers keep reinventing the feature registry on their own because agents need to know which code belongs to which feature. Second, they **validate features-cli's approach**: feature metadata in the repository, read by agents through files or MCP, is what these developers converge on without being told. Third, the signal is **weak**. Where star counts could be retrieved they are zero or close to it, and the GitHub API was blocked for the rest. What these projects show is a recurring idea among individual developers, not market pull. They also show that a scanner is cheap to build, so the scanner cannot be the moat. What none of them has done is agree on a format. No vendor has standardized one, which leaves room for something like an "OpenFeature for product features".

## Every stage has an owner, but nobody owns the feature

The six adjacent categories each organize data around a different unit, and none of those units is a "feature" in the sense the proposed SaaS means. Engineering-intelligence (SEI) tools organize around teams, developers and Jira epics. Jellyfish's "Deliverables" covers "epics, releases, or initiatives, however a team organizes its work" ([Jellyfish](https://jellyfish.co/solutions/software-delivery-management/)), and Gartner's definition of the renamed Developer Productivity Insight category contains no feature entity ([Gartner Peer Insights](https://www.gartner.com/reviews/market/software-engineering-intelligence-platforms)). Developer portals organize around services, with configurable blueprints in Port ([Port](https://www.port.io/blog/port-vs-jellyfish-engineering-intelligence)). Release and monitoring tools organize around the **feature flag**. Figma organizes around components ([Figma Help](https://help.figma.com/hc/en-us/articles/23920389749655-Code-Connect)). Spec-driven tools organize around spec files in folders such as `.kiro/specs/<feature>/` ([Finout on Kiro](https://www.finout.io/blog/what-is-kiro)).

| Category | Closest players | Unit of organization | How far toward the full chain | Missing |
|---|---|---|---|---|
| Work tracking / PM | Linear, Jira + JPD + Rovo, Productboard, Aha! | Issue, project, epic | Linear: issue → PR → Diffs review → Releases. Jira: broadest coverage, via marketplace apps | Production usage/errors (Jira–Pendo is early access only), design status |
| Engineering intelligence | Jellyfish, LinearB, Swarmia, DX, Faros | Team, developer, epic | Delivery metrics linked to tickets | Specs, flags, production health per code area |
| Developer portals | Port, Backstage, Cortex, OpsLevel | Service / custom blueprint | Ownership, scorecards, integrations | Automatic feature derivation; poor fit for monoliths and monorepos |
| Release / monitoring | LaunchDarkly, PostHog, Datadog, Sentry, Vercel | Flag, event, error | Flag → code refs → guarded release → rollback | Specs and design as first-class objects |
| Traceability / ALM | Jama, Polarion, Codebeamer, Azure DevOps | Requirement, work item | Requirement → test → release (compliance) | Runtime telemetry; priced for regulated industries |
| Design / spec-driven | Figma, Kiro, Spec Kit, OpenSpec, Augment Intent | Component, spec file | Design ↔ code components; spec → tasks → code | Release, flags, production; drift detection is mostly manual |

On the planning side, **Linear is the closest engineering-native competitor**. It launched in-app PR review (Diffs) in late May 2026, framed as a response to agent-generated PRs ([Linear](https://linear.app/now/code-review-should-be-fast)). Linear Agent now runs coding sessions ([Linear](https://linear.app/now/coding-sessions-for-linear-agent)). Releases ties CI/CD deployment environments to issues ([megachangelog](https://megachangelog.com/companies/linear)), and CircleCI shipped an official orb for it ([CircleCI](https://circleci.com/changelog/linear-releases-orb/)). What Linear lacks is the post-release half: no flag, error or usage panel turned up in 2026 sources. Atlassian covers the most stages but stitches them together. It has a Jira feature-flag module that DevCycle and ConfigCat plug into ([Atlassian dev docs](https://developer.atlassian.com/cloud/jira/software/modules/feature-flag/)), a Pendo integration in early access, and, as of May 2026, a Teamwork Graph with more than 150B connections opened to third-party agents through a CLI and MCP ([SiliconANGLE](https://siliconangle.com/2026/05/06/atlassian-opens-teamwork-graph-pushes-rovo-agentic-execution-team-26/)).

On the production side, **LaunchDarkly has the most links already**. It has code-reference scanning ([LaunchDarkly docs](https://launchdarkly.com/docs/home/flags/code-references/github-actions)), automatic flag links to Jira issues and GitHub PRs ([LaunchDarkly docs](https://launchdarkly.com/docs/eu-docs/home/flags/links)), and Highlight's error and replay data folded into Guarded Releases with automatic rollback ([LaunchDarkly](https://launchdarkly.com/blog/launchdarkly-acquires-highlight/)). Since 16 November 2026 it also has Release Autopilot, which reads PR diffs to wrap AI-generated code behind flags ([LaunchDarkly](https://launchdarkly.com/blog/introducing-release-autopilot/)). PostHog puts analytics, flags, experiments, replay and errors on one event stream, and "PostHog Code" builds features with instrumentation already in place ([PostHog](https://posthog.com/code)). Datadog made its own Feature Flags generally available in February 2026, natively tied to APM and RUM, and it opens cleanup PRs for unused flags automatically ([Datadog](https://www.datadoghq.com/about/latest-news/press-releases/datadog-launches-feature-flags/); [IT Brief](https://itbrief.co.uk/story/datadog-links-feature-flags-with-real-time-telemetry)). Sentry's flag-to-error correlation is still in open beta ([Sentry docs](https://docs.sentry.io/product/issues/issue-details/feature-flags)). Even inside one vendor the joins are unfinished: no Vercel feature was found that connects flag evaluations to rolling-release metrics ([Vercel docs](https://vercel.com/docs/rolling-releases)).

On the upstream side, Figma's MCP server has been generally available since October 2025. At Config 2026 Figma announced Code Layers (closed beta), which clones repositories into the canvas and syncs changes back ([CMSWire](https://www.cmswire.com/digital-experience/figma-launches-code-layers-motion-at-config-2026/)). Its unit is still the component, though, with no release or production state. Spec-driven tools store specs per feature in the repository, but drift detection is manual (Spec Kit's `/speckit.reconcile`, OpenSpec's `/opsx:sync`) or left to small open-source CLIs such as CorvidLabs spec-sync ([GitHub](https://github.com/CorvidLabs/spec-sync)). Augment Intent's "living specs" with a verifier agent is the one commercial claim of automatic sync, and it is in beta ([Augment](https://www.augmentcode.com/tools/intent-vs-kiro)). **No spec-driven tool reaches release or production.** Classic ALM tools trace requirement → test → release for ISO 26262 and IEC 62304 audits ([QKS Group](https://qksgroup.com/blogs/qks-review-the-split-in-alm-for-regulated-industries-enterprise-giants-vs-focused-specialists-1484)) and stop at deployment.

The gap is therefore genuine but narrow. Nobody models a feature as a superset of N flags, N code paths, N specs and tickets, a design file and its telemetry. The strongest single substitute is a customer hand-modelling a "Feature" blueprint in Port. A team could do that today, but it requires manual upkeep, which is exactly what kills portals.

## Incumbents are closing in from both ends, and buyers pay for platforms

The most important pattern in the 2024–2026 deal record is that **buyers paid for engineering data, but platforms captured the value**. Atlassian agreed to buy DX for about US$1B in September 2025, and "nearly all" DX customers were already Atlassian customers ([BNN Bloomberg/Reuters](https://www.bnnbloomberg.ca/business/2025/09/18/atlassian-to-acquire-developer-productivity-platform-dx-for-us1-billion/); [Constellation Research](https://www.constellationr.com/insights/news/atlassian-buys-dx-1-billion)). OpenAI bought Statsig for about $1.1B ([Bloomberg](https://www.bloomberg.com/news/articles/2025-09-02/openai-to-buy-product-testing-startup-statsig-for-1-1-billion)). Eight months later Amplitude took over Statsig's platform and customers while the team stayed at OpenAI ([Amplitude](https://amplitude.com/en-us/blog/amplitude-and-statsig-partnership.md)). Standalone flag vendors are being absorbed into larger stacks: Datadog bought Eppo ([Datadog](https://www.datadoghq.com/about/latest-news/press-releases/datadog-acquires-eppo-to-expand-its-ai/)), Harness folded in Split ([Harness](https://www.harness.io/press-and-news/harness-acquires-split-software-to-enhance-feature-management)), and LaunchDarkly bought Highlight. On the code side, Cursor bought Graphite ([Contrary Research](https://research.contrary.com/company/graphite)), and Harness acquired Augment's Context Engine and agent assets to "automate software from idea to production" ([Dealroom](https://dealroom.co/news/160997-harness-acquires-augment-code-to-automate-software-from-idea-to-producti/)). That phrase is close to the proposed SaaS's own pitch, and much larger companies are now saying it.

Port raised a $100M Series C at an $800M valuation in December 2025 to replace do-it-yourself Backstage and become an "agentic engineering platform" ([TechCrunch](https://techcrunch.com/2025/12/11/port-raises-100m-at-800m-valuation-to-take-on-spotifys-backstage)). Linear raised at $1.25B in June 2025 ([TechCrunch](https://techcrunch.com/2025/06/10/atlassian-rival-linear-raises-82m-at-1-25b-valuation/)), with a reported $2.5B tender in August 2026 that is secondary money and unconfirmed ([Dealroom](https://dealroom.co/news/147084-linear-doubles-valuation-to-2-5b-defying-the-saas-is-dead-narrative/)). Gartner gave the category legitimacy with a 2024 Market Guide, a renamed 2025 guide and a first Magic Quadrant in 2026 ([LinearB](https://linearb.io/resources/gartner-magic-quadrant-dpi-platforms-2026)).

The failures matter just as much. CodeSee is the closest analog to "map your codebase by area". It stopped commercial operations in February 2024 and its technology was folded into GitKraken ([SD Times](https://sdtimes.com/software-development/gitkraken-acquires-codesee-launches-new-devex-platform/)). Height shut down in September 2025 despite strong design ([AlternativeTo](https://alternativeto.net/news/2025/3/height-project-management-tool-to-shut-down-by-september-2025/)). Athenian, a DORA-metrics tool, quietly closed ([scrums.com](https://www.scrums.com/blog/athenian-alternative-dora-metrics)). Pluralsight Flow went to Appfire ([Appfire](https://appfire.com/newsroom/appfire-acquires-flow)), and competitor blogs report a sunset date that has not been verified. Productboard laid off about 30% of staff in April 2026 ([lupa.cz](https://www.lupa.cz/aktuality/productboard-propousti-tretinu-zamestnancu-radeji-rez-nez-pomale-krvaceni-rika-palan-o-ai-modelu-firmy/)). Two deaths bear directly on the feature-as-unit idea. Delibr, a Stockholm "feature refinement" document tool that synced PM feature write-ups to Jira epics, announced a full shutdown on 31 August 2026 ([Delibr](https://www.delibr.com)). It was the PM-only version of organizing work by feature, with no link to code or production. Pivotal Tracker, one of the best-known story-centric trackers, reached end of life on 30 April 2025 ([Pivotal Tracker](https://pivotaltracker.com/blog/2024-09-18-end-of-life)). The lesson is consistent: **a tool that visualizes data other systems own, without becoming part of a daily workflow, gets absorbed or dies**.

The same consolidation creates the counter-argument for a neutral layer. Each suite now keeps per-feature data inside its own ecosystem: LaunchDarkly guards releases with its own errors, Datadog correlates flags with its own APM, PostHog joins on its own event schema. A team that runs Linear, LaunchDarkly, Sentry and PostHog together has no place where these meet, and Statsig's customers face a forced renegotiation at renewal ([MarTech](https://martech.org/amplitude-and-statsig-deal-raises-questions-for-customers/)). Cross-vendor neutrality is a real position. It is also a position that depends on other people's APIs, some of which are plan-gated: LaunchDarkly's Code References API is Enterprise-only ([LaunchDarkly API docs](https://launchdarkly.com/docs/api/code-references.md)).

## Demand is inferred from AI churn, and features-cli has no pull yet

The best-evidenced pain is that **AI raises change volume and instability faster than teams can keep track**. DORA 2025 (nearly 5,000 respondents, about 90% using AI) found AI now raises throughput, but instability keeps rising with adoption ([DORA 2025](https://services.google.com/fh/files/misc/2025_state_of_ai_assisted_software_development.pdf); [InfoQ](https://www.infoq.com/news/2025/09/dora-state-of-ai-in-dev-2025)). GitClear's analysis of 211M changed lines found refactored ("moved") code fell from 24.8% to 9.5% of changes between 2021 and 2024, while duplicated blocks rose eightfold in 2024 ([LeadDev](https://leaddev.com/software-quality/how-ai-generated-code-accelerates-technical-debt)). That is a correlation, and it conflicts with DORA 2024's finding of a small quality gain. The 2025 Stack Overflow survey found 46% of developers distrust AI accuracy and only 3% highly trust it ([TechRepublic](https://www.techrepublic.com/article/news-developer-trust-in-ai-declines/)). Spec drift is debated actively on Hacker News, with skeptics arguing "there's nothing that couples the english language specs you've written with the actual code" ([HN](https://news.ycombinator.com/item?id=47422065)). Thoughtworks Radar Vol 35 reports that teams using coding agents are increasingly adopting spec-driven development, but places "AI-driven documentation sprawl" in Caution ([Thoughtworks](https://www.thoughtworks.com/content/dam/thoughtworks/documents/radar/2026/11/tr_technology_radar_vol_35_en.pdf)).

**None of this measures the pain the SaaS would sell against.** No survey quantifies "losing track of features", feature-level ownership confusion or post-ship visibility. Searches surfaced no primary Reddit or HN threads complaining that tools lose sight of features after they ship. The closest user complaints are generic, such as Linear's analytics being "thin" ([wearefounders](https://www.wearefounders.uk/linear-vs-jira-2025-is-linear-finally-ready-for-non-technical-teams/)). The pain is plausible and structurally visible in the tool sprawl, but it is not demonstrated.

The proposed product also has a structural problem with its buyer. Engineering-intelligence and portal tools are bought by VPs of Engineering, CTOs and platform leads and priced per developer. Product analytics and roadmap tools are bought by product leadership from a separate budget. A dashboard that spans "design and spec" (product) and "implementation, release and monitoring" (engineering) risks **having no single economic buyer**. No source showed a budget line for "feature visibility".

The failure record of all-in-one dashboards adds to the risk. An SRE leadership essay calls the single pane of glass "a recipe for being completely ignored" ([Medium](https://medium.com/site-reliability-engineering-leadership/the-single-pain-of-glass-6e42930e966)). Spotify's Backstage lead is quoted as saying external adopters often stall around 10% internal adoption ([byteiota](https://byteiota.com/backstages-89-idp-market-share-hides-10-adoption-crisis/)). That is a widely repeated anecdote, not a study. Gartner reportedly warns that teams "misconstrue Backstage as a ready-to-use portal" ([Roadie](https://roadie.io/blog/platform-engineering-in-2026-why-diy-is-dead/)). Claims that up to 90% of BI dashboards go unused are weakly sourced ([OWOX](https://www.owox.com/blog/articles/why-dashboards-fail)). The direction is consistent even though the numbers are soft: trust and catalog staleness kill these products, and an end-to-end feature dashboard faces both risks at every stage it adds.

Against that backdrop, features-cli's own signals are the weakest link. As of 19 November 2026 the repository has **11 stars, 0 forks, 0 watchers, and pull requests from only two authors: the maintainer and Dependabot** ([GitHub API](https://api.github.com/repos/interaction-dynamics/features)). It has 4,209 total crates.io downloads but only **140 in the last 90 days**, and the total is inflated by frequent releases and mirrors ([crates.io](https://crates.io/api/v1/crates/features-cli)). Searches found no HN, Reddit or blog mentions. npm downloads could not be checked. Shipping velocity is very high (over 200 PRs in about 13 months, covering an MCP server, health score, risk matrix and Spec Kit/Kiro readers), but velocity is not demand. The usual precondition for open-source-to-SaaS, a base of free users asking for hosted and team features, has not been met. The open-source models also warn about the conversion trigger. PostHog concluded that open source is "a great initial distribution channel but doesn't make for great monetization" ([PostHog](https://posthog.com/blog/open-source-business-models)). Sentry started hosting because self-hosting was "a huge pain to maintain" ([Sentry](https://sentry.io/resources/the-future-of-open-source-saas-the-final-frontier)). A stateless local CLI has no such pain. **The hosted value has to come from things the CLI cannot do alone: history, cross-repo views, collaboration, and enforcement in CI.**

## The defensible wedge is a feature registry for AI-heavy monorepos

Several assets in features-cli answer the specific weaknesses of incumbents. First, it **derives features automatically from folder structure**, which works in monoliths and monorepos. Service-centric portals fit those poorly because one service holds dozens of features. Second, its **metadata lives in the repository** (README front matter, `__docs__/specs`, generated CODEOWNERS), so the code is the source of truth. That avoids the catalog staleness behind the Backstage adoption problem. Third, it **aggregates by feature, never by person**, which sidesteps the surveillance criticism aimed at SEI tools. A JetBrains 2025 figure, reported secondhand, says 66% of developers doubt that metrics reflect their real contributions ([Macroscope](https://macroscope.com/content/measure-engineering-productivity-without-surveillance)). Fourth, it already **reads Spec Kit and Kiro specs and exposes an MCP server**, which fits where the agent-driven market is heading. The weakness is equally clear: the MIT license lets Port, Cortex or GitKraken embed it, so the moat cannot be the scanner itself.

The repository's integrations roadmap already names the right join principle: "the feature is the join key" (docs/roadmap/integrations.md in [interaction-dynamics/features](https://github.com/interaction-dynamics/features)). Matching runs through feature tags on events and errors, flag annotations in code, stack-trace paths and URL patterns. That matches how the market already joins release and production data. Sentry attaches recent flag evaluations to errors, flag-change webhooks mark suspect flags, and LaunchDarkly scans code for flag keys ([Sentry docs](https://docs.sentry.io/product/issues/issue-details/feature-flags); [LaunchDarkly docs](https://launchdarkly.com/docs/home/flags/code-references/github-actions)). The flag key is the de facto feature identifier at release time. A feature key that maps one feature to N flags, files, specs and telemetry sources sits one level above it, and no vendor owns that level.

The recommended wedge is therefore not a "dashboard" but **feature health checks for AI-heavy monorepos**. It would be a hosted service on top of features-cli that sells the four things a stateless CLI cannot provide. The first is **trends per feature over time**, which the roadmap rates as large effort for the CLI. The second is **cross-repo rollups by owner and team**. The third is **PR gates**: `features diff` posted as a check that flags new untested code, unowned files, specs that drifted from code, or stale flags touched by the change. The fourth is **continuous sync of ownership into Sentry and of flag hygiene against the flag provider**. Signals should go out to the places people already work (PR checks, CODEOWNERS, Slack, and agent context through MCP), and the web dashboard should be the place to look more closely, not the main product. The target customer is a GitHub-based engineering organization of 20–200 developers, working in a monorepo or modular monolith, using coding agents heavily, and running PostHog or Sentry. That segment is large enough to need ownership discipline and too small for Jellyfish, which reportedly "does not make sense below 200 developers" ([CodePulse](https://codepulsehq.com/guides/jellyfish-alternative)). The buyer is the VP of Engineering or platform lead, which avoids splitting the budget with product.

The wedge should leave out the two ends where incumbents are strongest. Design status belongs to Figma, which is building toward canvas-to-repo sync. Roadmaps and planning belong to Linear and Jira Product Discovery. Both stay link-out targets through the existing `links:` front matter, not features to build. Spec drift is the one upstream layer worth pursuing. Incumbents leave it manual, Thoughtworks' sprawl warning means buyers want specs pruned and validated rather than generated, and features-cli already reads the spec formats. Flag hygiene is valuable but contested: Datadog already opens cleanup PRs. features-cli's advantage there is that it works across providers, not that it exists.

### Framing it as SDLC by feature changes the positioning, not the verdict

Organizing the SDLC by feature is the right description of the end state, and the research shows the slot is empty. It does not change the verdict. The full platform still means competing with Linear's distribution, Atono's head start and Reflag's feature-first model all at once. It would also bring back the split-buyer problem, because planning and design belong to product while code, release and monitoring belong to engineering. What the framing changes is **what the product claims to be**. In three ways it sharpens the recommendation.

First, position the product as **the feature system of record: the shared feature ID that every other tool's artifacts point to**. It should not be pitched as "a dashboard" or as "a new place to plan work". features-cli's key is the strongest candidate for that ID because of how it is made. It is a slug derived from the folder and can be overridden in front matter, and the roadmap already describes it as "the value apps use to tag events, errors and issues" (docs/roadmap/integrations.md in [interaction-dynamics/features](https://github.com/interaction-dynamics/features)). It exists as soon as the code does, which Reflag's key does not, since that starts at flag creation. It survives after the story closes, which Atono's unit does not. And it survives after the flag is cleaned up and the project ends, which LaunchDarkly's and Linear's units do not. Reflag and Atono each make "feature" their noun, but only for part of the lifecycle. The code-derived key is the only one that spans all of it.

Second, **publish the key and front-matter format as an open specification**, and make it travel. That means importers for the YAML conventions developers are already inventing (`FEATURE-MAP.yaml`, `.features/*.yaml`, `.codebase/features/`), plus emitting the key into the places other tools read: OpenFeature evaluation context, Sentry tags, PostHog event properties, Linear and GitHub labels, and Backstage catalog entities. Earlier this report listed the MIT license as a weak moat. For a would-be standard it is a distribution asset. Third, **integrate rather than replace**. Under this framing, organizing the SDLC by feature means every tool's artifacts carry the feature ID, and the hosted product shows the joined record and checks it in CI. It does not mean rebuilding planning, flags or spec authoring.

The honest limit is that a solo maintainer with 11 stars cannot declare a standard into existence. The format wins only if it ships inside tools people already use: the MCP server, Claude skills, the Spec Kit and Kiro readers, and exports to Sentry and Backstage. And it wins only if at least one vendor or popular open-source project adopts it. That is why the validation plan below adds a format-adoption test.

### Pricing hypothesis

Market anchors make the price range clear. Per-developer pricing is the norm for this buyer. Charging on usage would compete with the per-event, per-MAU and per-session fees customers already pay to their systems of record ([usagepricing](https://www.usagepricing.com/blueprint/launchdarkly); [PostHog pricing](https://posthog.com/pricing)).

| Anchor | Reported price | Source quality |
|---|---|---|
| Port | Free to 15 seats; ~$30 (Basic) / ~$40 (Standard) per contributing dev/month | Vendor page via search ([Port](https://port.io/pricing)) |
| LinearB | $29 / $59 per contributor/month | Aggregator ([Sacra](https://sacra.com/c/linearb)) |
| Swarmia | ~$45–55/dev/month; modules $5–23/dev; free under 10 devs | Aggregator, conflicting ([Toolradar](https://toolradar.com/tools/swarmia/pricing)) |
| CodeScene | €18 / €27 per active author/month | Third-party blog ([repowise](https://repowise.dev/blog/comparisons/best-git-analytics-tools)) |
| Sentry Seer | $40 per active contributor/month | Vendor ([Sentry](https://sentry.io/about/press-releases/sentry-expands-seer-ai-debugging-agent)) |
| Atono | Free tier, then ~$19 (Starter) / ~$39 (Growth) per user/month | Aggregator; free-tier size conflicts ([xpay](https://www.xpay.sh/saas-pricing/atono-io/)) |
| Linear / Jira | ~$8–16/seat/month | Aggregators, conflicting ([automationatlas](https://automationatlas.io/answers/linear-pricing-2026/)) |

The hypothesis to test has four parts. The CLI, local dashboard and MCP server stay free and MIT-licensed. A hosted Team tier is free for up to 10 active contributors and then costs **$15–25 per active contributor per month**, counting anyone who committed in the last 90 days, as Port does. That sits below Port and LinearB and roughly where Swarmia's single-insight modules sit, which matches selling one sharp insight rather than a platform. An Enterprise tier adds SSO, RBAC, audit logs and self-hosting. Open-core experience suggests the jump to a roughly $25k-a-year commitment is triggered by SSO and compliance, not features ([Open Core Ventures](https://www.opencoreventures.com/blog/building-venture-scale-open-core)). The arithmetic is sobering: a 50-developer team at $20 pays $12k a year, so **$1M ARR needs roughly 80 such teams**. Given current traction, that is a multi-year path for a solo maintainer, not a quick bet.

## Validation steps, kill criteria and what would change the call

The thresholds below are judgment calls sized to a solo maintainer's time, not industry benchmarks. Their value is that they are written down before the results come in.

| Step | Timebox | What to measure | Continue if | Kill or defer the SaaS if |
|---|---|---|---|---|
| 1. Public CLI launch (Show HN, r/ExperiencedDevs, MCP and Claude/Cursor communities), positioned on "feature ownership and health for AI-written code" | 90 days | Stars, npm + crates downloads, external issues/PRs, teams running it in CI | 300+ stars, 1,000+ downloads per 90 days, 10+ external issues, 5+ orgs in CI | Under 100 stars and fewer than 3 external teams in CI. Keep it as an open-source portfolio project |
| 2. Discovery interviews with 15–20 VPs of Engineering or platform leads at 20–200-dev orgs | 4–6 weeks, in parallel | Rank of "which heavily used features are untested", "who owns this error", "which flags are dead", "does the spec still match" among top pains; what they use today | At least 6 of 15 put a feature-level ownership/health question in their top 3 and say current tools don't answer it | Most say Port, Backstage, LinearB or Linear already cover it, or the pain is "nice to know" |
| 3. Concierge design partners: run features-cli plus manually produced trends and PR comments | 8 weeks | Weekly use of the output; willingness to pay | 2+ of 5 sign paid pilots or LOIs (~$500–1,000/month) | 0 of 5 commit to pay after 8 weeks |
| 4. Join-key feasibility on partner codebases | Within step 3 | Share of Sentry errors and PostHog events matched to a feature through path mapping alone, with no app changes | 60%+ matched automatically | Under 40% matched without asking teams to tag code. The integration story then depends on customers doing the work |
| 5. Competitor watch | Ongoing | The likeliest gap-fillers come first. **Reflag** extending feature keys upstream into specs, PRs or errors; **Atono** adding production telemetry or a durable feature record above stories. Then: Linear adding Sentry/PostHog/flag panels; LaunchDarkly adding a "feature" grouping above flags; Port shipping a feature blueprint template; GitHub or Kiro shipping spec-drift views | None ships in the window | Two or more ship, or Reflag or Atono covers the full chain. Shift to being an integration or embedded component that exports the feature key into their products, not a standalone SaaS |
| 6. Open feature-ID format | 6 months, from launch | Publish the key and front-matter spec with importers for existing YAML conventions. Count external repos using it and tools that accept it (a flag vendor, spec tool or YAML-registry project) | 1+ external tool integrates it, or 20+ unaffiliated repos adopt it | No uptake. Drop the "system of record" claim and sell health checks on their own |

Evidence that would move the recommendation **toward the full end-to-end build** is strong inbound pull, meaning design partners asking unprompted for design and spec status alongside production health. It would also take proof of a joint product-and-engineering buyer willing to pay $30 or more per developer, and outside capital to compete with Linear's and LaunchDarkly's pace. Evidence that would move it **toward not building at all** is a flat CLI launch, interviews showing incumbents already answer the question, or Linear or Atlassian shipping per-feature production panels. A funded feature-first company could also fill the SDLC-by-feature slot: Reflag adding specs and error data to its feature keys, or Atono making its stories durable features with telemetry. In that case features-cli should feed its key into those products rather than compete with them. In either case the best outcome is a well-integrated open-source tool: the roadmap's Backstage catalog export and Sentry ownership rules make features-cli useful inside other platforms and a plausible acquisition or partnership target. That is a respectable result, given that every exit in this space has gone to a platform owner.

## Conclusion

The research changes the question. The issue is not whether an SDLC-by-feature platform is missing. It is. The gap persists because five camps each use "feature" for a unit with a different lifetime, because feature-level joins are hard to keep accurate, and because no single budget owns them. Platforms are filling the gap from both ends, one adjacent stage at a time, and each will lock its slice inside its own ecosystem. The scarce asset is therefore not another dashboard. It is the **shared feature ID** that every camp could reference, and developers hand-writing YAML registries for their agents are already asking for one. features-cli's claim to that role is narrow but real: a repository-native, automatically derived key that stays current because the code is the source of truth and outlives every story, flag and spec attached to it. Products built on that key can stay neutral across vendors in a way Linear, LaunchDarkly, PostHog, Reflag and Atono cannot.

The deciding variable is adoption, not competition. A tool with 140 downloads a quarter cannot yet tell whether teams want feature-level health at all. The cheapest information available is a real launch and five design partners, not a hosted backend. If the CLI earns pull, the SaaS should sell trends, PR gates and cross-repo views of feature health to AI-heavy monorepo teams at Port-minus pricing. If it does not, building a dashboard on top would only make the gap more expensive to keep open.
